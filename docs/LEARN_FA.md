# حافظه و تاریخچه در برنامه‌های LLM

## ۱. مدل چگونه چیزی را یادش می‌ماند؟

در API معمول گفتگو، برنامه اطلاعات موردنیاز را دوباره به مدل می‌دهد. ذخیره‌شدن پیام در دیتابیس به‌تنهایی باعث دیده‌شدن آن توسط مدل نمی‌شود.

- **History:** آرشیو پیام‌ها و نقش گوینده.
- **Memory:** اطلاعات نگهداری‌شده یا بازیابی‌شده برای استفادهٔ بعدی.
- **Context:** اطلاعاتی که همین بار واقعاً به مدل می‌فرستیم.

این پروژه context می‌سازد؛ مدل اجرا نمی‌کند.

## ۲. پیام‌های اخیر

روش recent از آخرین پیام شروع می‌کند. ادامهٔ گفتگو حفظ می‌شود، ولی تصمیم قدیمی ممکن است حذف شود. این نسخه پیام‌ها را جدا انتخاب می‌کند؛ در برنامهٔ واقعی شاید لازم باشد سؤال و جواب یا فراخوانی ابزار و نتیجهٔ آن را یکجا نگه داری.

## ۳. فشرده‌سازی با خلاصه‌سازی فرق دارد

روش compact فقط ۱۰۰ نویسهٔ اول هر پیام را می‌گیرد. این **خلاصه‌ساز هوشمند نیست**؛ برای دیدن هزینهٔ حذف اطلاعات است. اگر اصلاح تصمیم در پایان پیام باشد، ممکن است حذف شود. پرچم truncated این اتفاق را نشان می‌دهد و اصل پیام در دیتابیس باقی می‌ماند.

در خلاصه‌سازی با مدل باید تصمیم‌ها، منابع و سؤال‌های باز حفظ شوند و خروجی از نظر حذف یا ساختن اطلاعات بررسی شود.

## ۴. بازیابی

روش retrieve تعداد واژه‌های مشترک سؤال و پیام را می‌شمارد. در امتیاز برابر پیام جدیدتر اولویت دارد. حروف ي/ی و ك/ک یکسان می‌شوند؛ نرمال‌سازی کامل فارسی انجام نمی‌شود.

Embedding می‌تواند برخی بازنویسی‌ها را پیدا کند، ولی شباهت به معنی صحت نیست. این نسخه بازیابی برداری ندارد و یک خط مبنای ساده برای مقایسهٔ آینده است.

## ۵. روش ترکیبی و تغییر تصمیم

Hybrid یکی از پیام‌های مرتبط و یکی از پیام‌های اخیر را به نوبت بررسی می‌کند. تکراری‌ها حذف و خروجی به ترتیب زمان مرتب می‌شود.

در دمو ابتدا PostgreSQL انتخاب شده، سپس برای نمونهٔ محلی SQLite جایگزین شده است. بازیابی هر دو پیام می‌تواند تغییر تصمیم را نشان بدهد. کد خودش تناقض را حل نمی‌کند؛ شناسهٔ منبع برای بررسی آن حفظ شده است. جدیدتر بودن همیشه نشانهٔ درست‌بودن نیست، مخصوصاً اگر پیام حدس دستیار باشد.

## ۶. بودجه

گزینهٔ budget سقف **نویسه‌های JSON شواهد** است؛ دستور سیستم و سؤال در این سقف نیستند. نویسه با token برابر نیست، مخصوصاً در فارسی. برای مدل واقعی باید tokenizer همان مدل و فضای پاسخ را حساب کنی.

## ۷. ماندگاری، حریم گفتگو و فراموشی

SQLite می‌تواند تاریخچه را پس از بستن برنامه نگه دارد؛ دمو عمداً فایل موقت دارد. Session جلوی مخلوط‌شدن دو گفتگو در این API را می‌گیرد، اما احراز هویت نیست. فایل دیتابیس رمزگذاری نشده است.

حافظهٔ بلندمدت ساختاریافته می‌تواند ترجیح تأییدشدهٔ کاربر همراه منبع و زمان انقضا باشد. آن را هنوز پیاده نکرده‌ایم؛ هر جمله نباید حقیقت همیشگی فرض شود. forget فقط حذف منطقی ردیف‌هاست و نسخه‌های پشتیبان را پاک نمی‌کند.

## ۸. تمرین

```bash
python -m memory_lab --budget 450
python -m memory_lab --budget 1200
python -m memory_lab --query "What language for the tutorial?"
python -m unittest discover -s tests -v
```

۱. ببین هر روش پیام تغییر دیتابیس را نگه داشته یا حذف کرده است.
۲. سؤال را بدون واژهٔ database بازنویسی کن؛ بازیابی چه چیزی را از دست می‌دهد؟
۳. اصلاح تصمیم را در انتهای یک پیام طولانی بگذار و compact را امتحان کن.
۴. دو session بساز؛ یکی را حذف کن و باقی‌ماندن دیگری را بررسی کن.
۵. budget را به ۲ کاهش بده؛ خروجی خالی معتبر است و نباید با اطلاعات ساختگی پر شود.

## مرور

- ذخیرهٔ پیام یعنی مدل آن را دیده؟ **نه؛ باید در context قرار بگیرد.**
- بازیابی یعنی حقیقت؟ **نه؛ منبع، زمان و تناقض را بررسی کن.**
- کیفیت جواب مدل سنجیده شده؟ **نه؛ تست‌ها مربوط به انتخاب شواهد و ذخیره‌سازی‌اند.**
- چرا اصل پیام را نگه می‌داریم؟ **برای بررسی حذف‌ها و ارجاع به منبع.**

از core.py شروع کن و سپس تست‌ها را بخوان. [مقالهٔ رسمی Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) توضیح بیشتری دربارهٔ compaction و یادداشت‌های ساختاریافته دارد.

## ۹. ارزیابی روش‌های حافظه در نسخهٔ ۰٫۲

```bash
python -m memory_lab.evaluate --budget 450
python -m memory_lab.evaluate --budget 900 --output evaluation.json
```

پنج سؤال ساختگی داریم و برای هر سؤال شناسهٔ منبع و عبارت لازم مشخص شده است. هر چهار روش با سقف یکسان اجرا می‌شوند؛ گزارش نشان می‌دهد کدام منبع یا عبارت حذف شده است.

**Source recall** می‌گوید چند منبع لازم انتخاب شده‌اند. اما ممکن است منبع انتخاب شود و قسمت مهمش بریده شود! برای همین **excerpt recall** هم داریم: عبارت لازم باید واقعاً در متن انتخاب‌شده باقی مانده باشد. در مثال تغییر دیتابیس، اصلاح تصمیم آخر یک پیام بلند است؛ compact ممکن است شناسه را نگه دارد ولی اصلاح را حذف کند.

**Source precision** سهم منابع موردانتظار از کل منابع انتخاب‌شده است. برای خروجی خالی صفر در نظر گرفته شده است. میانگین‌ها روی سؤال‌ها محاسبه می‌شوند و وزن هر سؤال یکسان است، حتی اگر دو منبع بخواهد.

تمرین: بودجه را از ۴۵۰ به ۹۰۰ تغییر بده؛ آیا منبع اصلاح تصمیم جا می‌شود؟ سپس سؤال paraphrase را ببین: نبودن واژهٔ مشترک چگونه بازیابی را ضعیف می‌کند؟

این عبارت‌ها دقیق و حساس به بزرگی حروف مقایسه می‌شوند؛ ارزیابی معنایی نیستند. مجموعه کوچک و آموزشی است، نه آزمون مستقل برای اثبات برتری روش‌ها. کیفیت جواب LLM هم هنوز اندازه‌گیری نمی‌شود.
